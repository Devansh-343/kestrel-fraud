# Kestrel Home: warranty claim review

Scores each warranty claim before payout and says whether the investigation desk should look at it, in rupees,
with plain-English reasons. Built for the Kestrel Home Variant C pack.

**The short version:** "Accuracy above 97%" is met by a model that never flags anything (96.9–99.3% every month),
so I optimised for what Finance asked for instead: rupees of fraud stopped per claim checked, under the 40-a-month
desk limit. In a month-by-month backtest (Jan–Jun 2026) the model sent ~9 claims a month to the desk and netted
**Rs 1.27 lakh over six months (~Rs 21,000/month, Rs 2,307 per review)**. Reviewing the 40 highest-probability claims
each month nets only Rs 25,600; reviewing 40 random claims from new partners loses Rs 1.31 lakh.

The bigger finding is not the model: since the May auto-approve change, **7 specific outlets** (out of 60 new
partners) account for 33 of 35 frauds among small uninspected claims. See `memo.md`.

## Run it (clean machine, no API keys)

Requires Python 3.10+.

```bash
git clone <this repo> && cd kestrel-fraud
python -m venv .venv && source .venv/bin/activate      # Windows: .venv\Scripts\activate
pip install -r requirements.txt

# The client data is NOT in this repo (ops-policy §10 forbids publishing it).
# Copy the five CSVs from the data pack into ./data with these names:
#   data/train.csv  data/test_unlabelled.csv  data/products.csv  data/partners.csv  data/sample_submission.csv

python src/train.py          # ~20 s: backtest, final model, predictions.csv, reports/
uvicorn app.main:app --port 8000
```

Open http://localhost:8000 and click one of the example claims.

If `artifacts/` is missing the service exits with a message telling you to run `src/train.py`. No paid API or
external service is used anywhere, so there is nothing to fail without a key.

### API

`POST /score` with one claim:

```json
{"partner_id": "SP3129", "sku": "KH-CF-03", "claim_amount_inr": 1995, "days_since_purchase": 12,
 "photo_attached": "Y", "partner_inspected": "N", "customer_prior_claims": 0,
 "submitted_at": "2026-07-24 19:38"}
```

returns

```json
{"fraud_probability": 0.6154, "expected_saving_rs": 821, "decision": "review",
 "summary": "Send to the investigation desk: about 62% chance of fraud; reviewing it saves Rs 821 on average.",
 "reasons": [{"reason": "SP3129 has 4 past claims confirmed as fraud (9% of its decided claims, smoothed)", "effect": 0.612},
             {"reason": "SP3129 sent 11 claims in the last 60 days", "effect": 0.433},
             {"reason": "Under Rs 2,000 and not inspected, so it would be auto-approved", "effect": 0.421}],
 "notes": [], "partner_data_as_of": "2026-09-30 23:46:00"}
```

Unknown SKUs return a 422 with a readable message; unknown partners are scored with average partner history and a
note saying so. `GET /health` reports which partner snapshot is loaded.

## How it decides

`expected saving = P(fraud) × claim amount − (1 − P(fraud)) × Rs 380 − Rs 260` (ops-policy §4: goodwill for a held
genuine customer, cost of a service contact). Review only if that is positive, highest first, at most 40 a month.
That rule is why the queue is short: a Rs 1,500 claim needs ~34% fraud probability before a review pays for itself.

## Data decisions

- **Duplicate claim numbers** (re-submissions, 681 pairs): kept the latest submission. Pairs never disagree on outcome.
- **Undecided cases**: blank `is_fraud` (215 rows) dropped from training and evaluation. Zoho could not store
  blanks, so ~3% of pre-Oct-2025 "0" labels are probably undecided cases. CRM undecided cases look like genuine
  claims on every feature, so I kept the Zoho zeros: the expected contamination is 1–2 mislabelled frauds.
- **Serials**: normalised (upper-case, strip spaces and dashes). Serial reuse turned out *not* to predict fraud
  (collisions are common across unrelated SKUs), so it is not a feature.
- **Timestamps**: `submitted_at` is IST in both systems. The UTC issue in §9 is about resolution events, which are
  not in this export, so no conversion was needed.
- **Partner history** features only use claims submitted before the claim being scored, and fraud outcomes
  decided before the scoring month, so the backtest is not looking into the future.
- **Partner age is deliberately not a feature.** Adding it changed backtest net savings by ~3% (one claim). The
  model already finds the problem outlets by behaviour, and Meenal asked not to penalise new partners as a group.
